一、项目定位与边界

  • 独立项目：新仓库（建议名 aoi-qqbot），承载 relay v4（双向版）与配套测试；Aoi-system 主仓库

仅在最终接入时做两处小改动（见五·M4，均可独立回退）。

  • 不做的事：不做群聊闲聊/关键词自动回复以外的任何自动化；不动现有单向推送链路的行为；

不在群里公开任何成员个人数据（查单结果一律私聊回复）。

  • 复用前提：v3.4.0 已上线的两个后端能力是本项目的基础——

① update_team_data_by_member_key(..., p_cn) 白名单写入口（绑定 QQ 复用它，无需新写入口）； ② get_team_by_member_key(member_key, p_cn) 按 CN 裁剪读（查单数据源）。

三、架构（在现有链路上的增量）

QQ 群/私聊 ⇄ NapCat ──上行事件(HTTP POST)──▶ relay v4（ECS，同机）
                                              ├─ /             单向推送（现有，不动）
                                              ├─ /onebot/event  上行事件接收（新）
                                              │    ├─ 解析指令 → 去重/限频 → 白名单群校验
                                              │    ├─ 查数据：调 Supabase 团员 RPC（anon 身份）
                                              │    └─ 回复：经 NapCat send_private_msg
                                              └─ NapCat HTTP API（现有）
  • relay v4 改造（relay/relay.js 同仓升级）：新增 POST /onebot/event 端点接收 NapCat 上行

（NapCat 配置 HTTP POST 上报地址指向它）；事件按 message_id 去重防重放；文本指令解析 （前缀「查单/我的进度/绑定/帮助」，大小写与空格容错）；串行队列复用现有节流。

  • 新增 1 个 Supabase RPC（主仓库，M4 时合入）：member_lookup_by_qq(p_qq text) ——

security definer；按 memberMeta 把 QQ 解析到 CN 后，只返回该成员的订单/交费状态摘要与看板地址， 不返回整 blob、不含任何他人数据（字段级设计见附录）。

  • 绑定流数据路径：密钥+CN 校验 = 调现有 get_team_by_member_key(key, cn)（返回 null 即密钥/圈名不符）

→ 通过后调 update_team_data_by_member_key(key, {memberMeta:{cn:{qq}}}, null, cn)（B2 白名单已覆盖此写法）。 全程不新增存储，绑定关系仍以 blob memberMeta 为唯一事实源。

四、安全与防滥用

  • 白名单群：relay 只处理配置群号的上行 @ 消息（env ALLOWED_GROUPS），其他群一律忽略。
  • 限频：每 QQ 每分钟 ≤3 条指令、每分钟全局 ≤30 条；超限静默丢弃并记日志。
  • 私聊兜底：群内指令一律私聊回复；查不到绑定关系时回复引导语（附网页绑定地址），不泄露存在性。
  • 凭证纪律：绑定密钥只在单条消息生命周期内存在，处理完即置空；relay 日志对该消息体打码（只记指令类型与 QQ 尾 4 位）。
  • 事件防重放/防伪造：NapCat 上报走 127.0.0.1（同机 host 网络，不走公网）；message_id 去重（内存 + 5 分钟过期）。
  • 审计：relay 把每次指令（类型/QQ 尾号/结果）追加到本地 JSONL 日志，供排查。
