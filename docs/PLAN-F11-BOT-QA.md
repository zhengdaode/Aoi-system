## 一、Jev（TypeSafe）适用性评估

### 1.1 是什么（引 PLAN-TYPESAFE 定义）

> System One 模型（旗舰 Jev）把语义判断做成编程原语——输入自然语言+应用状态，输出**带概率的类型化判断**
> （Choice 选一项 / Noul 是否概率 / Score 等级分），**不生成文本**，~150ms 级延迟。

### 1.2 与本需求 7 条的匹配度

| 需求 | Jev 适配 | 说明 |
|------|---------|------|
| ② 自然语言猜指令 | ✅ 完美适配 | `choice(意图：查单/我的快递/团况/绑定/解绑/我是谁/帮助/转人工/其他)`——就是 T8 原案 |
| ④ 剔除无意义语句 | ✅ 适配 | `noul(这条消息是否包含有效诉求？)`；前置确定性预筛（第二节 4.3）压送判量 |
| ④ 自动标注重要事件 | ✅ 适配 | `score(紧急度)` + `choice(分类)`；确定性关键词层兜底 |
| ④ 每日 timeline 汇总 | ⚠️ 部分适配 | **拼装 timeline 是确定性代码**（Jev 不生成文本）；Jev 只负责打标 |
| ③⑤ 转人工 / 管理员筛选 | ⭕ 不需要 AI | 纯指令 + 确定性过滤排序，本地数据即可 |
| ①⑥ 规范查询 / 绑定 | ⭕ 不需要 AI | F5/F10 已实现 |
| 「自动问答」若指生成式回答 | ❌ 不适配 | Jev 不生成文本。买家问「国际费怎么算」只能路由到帮助/看板，不能生成解释。若要生成式问答需另接生成式 LLM 通道（需单独评估选型与安全）——**本提案明确不做**，理由见 1.4 |

### 1.3 利

1. **基建现成**：Edge 代理（密钥管理/限频/超时/重试/降级）、`deploy-edge.js` 部署通道、设置页开关、
   「级联不回退」纪律全部是 v3.18.0 已验收的存量；T8 端点主仓库可先行交付，不依赖 SWAS relay。
2. **输出可编程、不胡说**：类型化判断 + 概率，低置信回「帮助」引导，符合「确定性优先、低置信升级人工」
   五条集成纪律；不存在生成式 LLM 的幻觉与提示注入面（买家原话进不来 system prompt）。
3. **延迟与成本友好**：~150ms 级判断、按次计费远低于生成式；量级估算见第五节。
4. **绕开 SDK 版本约束**：TypeSafe JS SDK 需 Node 20+，relay 是 Node 18 零依赖单文件——走 Edge HTTPS
   通道（内置 fetch）天然绕开，relay 保持零依赖。

### 1.4 弊与缓解

| 弊 | 缓解 |
|----|------|
| 只能做封闭候选集判断，无法生成式答疑 | 定位收窄为「意图路由 + 打标」；答疑=引导到标准指令/看板/转人工。若日后要生成式，另立提案单独选通道并评估提示注入/内容安全/风控 |
| 新增外部依赖链 relay→Edge→api.typesafe.ai | 级联不回退：中文裸词精确命中优先（现状逻辑不动），未命中才送判；Edge 超时/报错**静默回落现状「帮助」文案**，任何现有行为不变差 |
| 买家消息量不可控 → 送判成本可被刷爆 | relay 侧三重闸：每 QQ 限频已有（3 条/分）+ **每 QQ 每日送判上限（默认 5 条，超出直接回帮助）** + 全局每日送判上限（env `LLM_DAILY_LIMIT`，默认 200） |
| typesafe-proxy 现只认 Aoi 管理员 token，买家不是管理员 | Edge 新增 `/bot-intent` 端点 + **bot 专用共享密钥鉴权**（`BOT_INTENT_TOKEN` 存 function secrets + relay `.env` 两侧比对，与 EVENT_TOKEN 同款纪律）——T8 原案的鉴权缺口，本提案补上 |
| 送判内容是买家原话，可能含手机号/地址 | 最小化送判：只送文本（截断 ≤200 字）+ 候选清单，**不含 QQ/圈名**；手机号正则脱敏后再送；审计仍只记类型+QQ 尾 4 位 |
| 判断质量依赖阈值校准 | 沿用 TypeSafe 官方要求「thresholds evaluated on the user's data」：上线前用真实 unknown 消息存档跑一周影子模式（只记录不生效）定阈值 |

## 二、七项需求逐条分析与迭代（「迭代改进我的思路」）

### 需求① 规范提问格式 → 调绑定数据回复 —— **已实现，无需新开发**

现有指令已覆盖：`查单 [活动名] / 我的进度 / 我的快递 / 我是谁 / 团况 / 绑定 / 解绑 / 帮助`，
数据链路 `member_lookup_by_qq`（anon RPC，只回本人摘要）。迭代点：帮助文案归入 F11 统一更新，
「规范格式」即帮助里的清单——新功能的职责是把不规范的输入**引导回**这份清单。

### 需求② 非规范自然语言 → Jev 猜意图 + 提示用帮助 —— **T8 落地，行为分层迭代**

原思路「调用 jev 模型猜测其想问的内容对应的命令」成立，迭代为三级响应（**模型只提示、不直接执行**）：

- **高置信（≥阈值）**：`您是想「查快递」吗？直接发送【我的快递】即可～`——回显猜测 + 给出可复制的标准指令，
  买家自己发指令才触发查询（写操作类指令如绑定/解绑**永不**自动执行，哪怕高置信）。
- **中置信**：列 2–3 个猜测`您是想：① 查单 ② 我的快递 ③ 转人工？回复对应指令即可，发送【帮助】看全部`。
- **低置信/其他**：现状文案不变`没听懂这句…发送『帮助』看看我能做什么～`。

迭代理由：① 兜住「猜错」的风险面（猜错文案比猜错执行安全得多）；② 每次送判同时让 Jev 顺带产出
分类/有意义/紧急度三个判断（一次请求多问并行，复用一条成本），供需求④归档直接消费。

### 需求③ 不满意 → 转发管理员 —— 新指令 `转人工`

- `转人工 <内容>`（私聊；群内 @ 发「转人工」→ 引导私聊，防他人诉求暴露在群里）。
- 防刷：每 QQ 每日 ≤3 条（独立于指令限频），超限回提示；内容 ≤500 字，超出截断并注明。
- 管理员收到的转发带来源标注：`【转人工 #A20250925-01】圈名xx（QQ尾1234）：内容`；
  买家收到确认 + 编号（编号规则见 4.2，可拿编号查进度）。
- 立即转发（不等每日汇总）；紧急问题同时进 timeline 并标⚠。

### 需求④ 归档 + 剔除无意义 + 每日 timeline + 重要标注 —— 核心新增，标准草拟如下（供改）

**4.1 归档什么**：所有私聊文本消息 + 群内 @bot 消息（含指令命中与 unknown），落
`data/questions/YYYY-MM.jsonl`（沿用 DATA_DIR 纪律，零 schema；按月分文件，保留 90 天自动清理）。

**4.2 记录结构**（一行一条，字段为设计值）：

```
{ "id":"A20250925-01", "ts":"2026-09-25T13:00:00.000Z", "qqTail":"1234", "cn":"圈名或空",
  "channel":"private|group", "raw":"原文截断500字", "how":"command|unknown|forward",
  "category":"进度咨询|物流快递|交费问题|绑定账号|商品咨询|投诉不满|其他",
  "importance":0-100, "meaningful":true, "status":"open|forwarded|resolved" }
```
编号 `A<日期>-<当日序号>`，即转人工确认号与 timeline 引用号，同一套。
`ts` 用 ISO 8601（与现有 relay-audit.jsonl 同源）；文件名 `YYYY-MM` 按自然月。

**4.3 剔除无意义（两级，顺序固定）**：

| 级 | 方式 | 规则 |
|----|------|------|
| L1 确定性（零成本） | 正则/长度 | 纯表情/纯@/空或长度<2/纯数字≤4位/口令式打招呼（"在吗""hello"单独出现计 low，不丢弃——打招呼也可回复帮助） |
| L2 Jev（仅 L1 未过滤的 unknown 消息） | `noul(是否含有效诉求)` | false → 记 `meaningful:false`，不进 timeline、只计入「噪声 N 条」统计 |

指令命中的消息不走 L2（能解析即有意义），按指令类型直接归类（查单→进度咨询…），**零 AI 成本**。

**4.4 重要事件判定标准（草拟，两层）**：

| 层 | 规则 | 动作 |
|----|------|------|
| R1 确定性关键词（先跑，零成本） | 命中 `退款｜投诉｜丢件｜丢失｜破损｜错发｜少发｜假的｜举报｜骗｜报警` | **紧急**：即时私发管理员（不等日结），timeline 标🔴 |
| R2 Jev 打标（unknown + 转人工消息） | `score(紧急度 0-100)` | ≥80 紧急（同 R1）；40–79 重要⚠（进 timeline 置顶段）；<40 普通 |

分级动作汇总：🔴紧急=即时转发+日结置顶；⚠️重要=日结置顶；⚪普通=按时间序入列。
补充规则：`status=open` 超 24h 的转人工问题，次日日结里重复提示「仍未处理」。

**4.5 每日 timeline（确定性拼装，Jev 不参与生成）**：
每日 21:00（env `DIGEST_HOUR` 可配）私发管理员一条，形态草拟：

```
【今日问题时间线 · 09-25】有效 7 / 噪声 3 / 转人工 1 / 紧急 1
🔴 14:02 [投诉不满] 圈名xx（QQ尾1234）：收到谷子有破损，要求补发…（#A03，已即时转发）
⚠️ 10:15 [物流快递] 圈名yy（QQ尾5678）：快递停在一周没动了（#A01）
⚪ 09:30 [进度咨询] （QQ尾9012）@bot 问进度（已答）
⚪ 12:40 [交费问题] 圈名zz（QQ尾3344）：国际费能不能分期…
—— 未处理待跟进：#A01 #A03
（回复「问题列表」看全部，「问题详情 编号」看原文）
```

**4.6 与需求的差异点（我改了思路的地方）**：原话「剔除无意义的语句」若理解为**物理删除**，
改为**降级标记**（`meaningful:false` 仍归档不展示）——误杀可追溯，管理员侧可翻；存储成本忽略不计。

### 需求⑤ 管理员开关 + 按条件筛选排序 —— 新增管理员指令组

- 开关：`关闭总结` / `开启总结`（仅 `botConfig.adminQq` 生效；状态持久化 relay 本地
  `question-digest-state.json`，防重启丢）。日结/即时转发都受它管：关闭后**只归档不推送**，
  随时开回并补看「问题列表」。网页设置页同步开关（`botConfig.digestEnabled`）列为可选后续。
- 查询（全部 relay 本地数据 + 确定性过滤，零 AI 成本）：
  - `问题列表 [今天|昨天|近7天] [类型：物流快递|…] [未处理] [按重要度]`
    —— 默认今天、时间倒序；`按重要度` = importance 降序；`类型：` 对应 4.2 分类；
    `转人工` 来的问题即「被转发给管理员的问题」，用 `类型：投诉不满` 或来源标记筛。
  - `问题详情 <编号>`：回原文+状态+时间线（归档/转发/处理时间）。
  - `问题处理 <编号>`：open → resolved（审计留痕）。
- 管理员身份沿用 `botConfig.adminQq`（设置页已有，单管理员先例）；多管理员列为开放问题（第九节）。

### 需求⑥ QQ + CN 绑定、是否需额外验证 —— **已实现，评估结论：不需要再加验证**

现状已是双通道验证式：bot 端 `绑定 <团员密钥> <圈名>`（密钥+圈名双验 + QQ 唯一性校验 + 密钥即用即焚 +
解绑需密钥防冒用）；网页端登录态绑定（声明式，配合唯一性校验）。
**评估**：密钥本身就是「持有即授权」凭证，且绑定错损的只是查询路由（可解绑重绑），不是资金/数据安全；
再加验证码（bot 发码→网页回填）防的是「网页账号被盗后恶意绑 QQ」这一低收益场景，摩擦成本高于风险。
**建议维持现状，明确不做**（与 F10 决策一致）。需求⑥零开发量。

## 三、架构与数据流

```
买家 QQ ⇄ NapCat（:3000，待装于 47 同机）
   │ HTTP POST 上报（现有）
   ▼
relay v4（aoi-qqbot relay.js 增量，零依赖不变）
   ├─ parseCommand 精确命中（现状逻辑不动）──→ 现有 handlers + 归档(how=command)
   ├─ unknown → 手机号脱敏/截断 → POST Edge /bot-intent（BOT_INTENT_TOKEN）
   │     ▲级联不回退：Edge 超时/报错/超日配额 → 静默回落「帮助」文案
   │     └─ 返回 {intent+置信度, meaningful, category, importance}（一次多问）
   ├─ questionStore：data/questions/YYYY-MM.jsonl 追加 + 当日内存索引
   ├─ 紧急(R1/R2) → 即时私发 adminQq（受总结开关）
   ├─ 转人工 → 即时私发 adminQq + 回执编号
   └─ schedulerRegister({hour:DIGEST_HOUR},'questionDigest') → 每日 timeline
          + 每日清理（90 天）+ 重复未处理提示
主仓库 supabase/functions/typesafe-proxy（增量）
   └─ POST /bot-intent：BOT_INTENT_TOKEN 校验（非 admin 通道）→ TypeSafe HTTP API
```

- **Supabase 数据库：零 schema 改动、零新表**。归档在 relay 本地（与审计 JSONL 同纪律）；
  若日后要网页端「问题工作台」，再立提案迁 Supabase 表（顺带解决多管理员）。
- relay 保持 Node 18 零依赖单文件：只新增纯函数模块（store/预筛/渲染）+ 两个 handler + 一个定时任务。
- 测试沿用 `setUpstreamFetch` 桩模式：Edge 桩测降级/超时/配额、预筛纯函数用例、digest 渲染快照。
