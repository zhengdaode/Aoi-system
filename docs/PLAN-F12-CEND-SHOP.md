# PLAN-F12 · C 端购物系统（买家自助商城）——调研、计划与演示

> 2026-09-30 立项。目标：面向买家（团员/散客）的淘宝式移动端购物 C 端——**按团期选购 → 购物车下单 → 支付 → 物流与个人资料**。
> 本文档先回答三个前置问题（①功能范围 ②现有部署能否支撑运营 ③现有「密钥+CN/QQ」鉴权是否够安全），
> 并交付静态演示 `demo/shop-demo/`（纯 UI 壳 + mock 数据，零后端、零主仓库代码改动）。
> **状态：待批准**——批准后按「六、版本切分」逐版实施，遵循 AGENTS.md 纪律（每改动一个 commit、测试全绿）。

## 一、现状摸底：C 端有什么家底可复用

购物 C 端不是从零建商城——管理端多年迭代沉淀的资产恰好是「卖场侧」的数据与链路，C 端主要是**换一个面向买家的壳 + 补交易闭环**：

| 现有资产 | 位置 | C 端复用方式 |
|---|---|---|
| 商品主档（唯一） | `activityMeta[].products`：refImage/refUrl/price/priceOrig/currency/limit（v3.7.0 起） | **商品橱窗数据源现成**——图/价/限购/原名全有，缺的只是「上下架开关 + 橱窗文案」两个字段 |
| 团期（活动）台账 | `d.activities` + `activityMeta[].ip/status/shipDate/link`（阶段 6） | 「按活动选购」= 团期列表/详情页，截团状态可由 status+shipDate 推导 |
| 订单全链路 | `orders`（到货批次/国际费/交费审批/发货/快递单号/收货确认） | **C 端下单直接落 `orders`，buyer=CN**——到货分批、国际费分摊、审批、发货、团员端查询全部零改造沿用 |
| 物流展示 | `orders.tracking/photo/shipped/shippedAt` + 团员端进度链（v3.4.0 F2） | C 端订单时间线直接复刻 `Aoi.member.progressChain` 口径 |
| 个人资料 | `d.addresses`（只写不读）、`memberMeta[cn].qq`、`cnChanges` | 资料/地址/QQ 绑定/改圈名申请全部有现成端到端链路 |
| 消息触达 | `notify` 三选推送 + QQ bot 双向（F5）+ 工单台「转人工」（v3.21.0） | C 端通知中心、催付/发货提醒、售后客服入口全部现成 |
| 囤货地 | `warehouses`（名称+收款码 URL） | **收款码展示位现成**——V1 支付方案的收款码直接用囤货地配置 |
| 限购与配货 | `limitPlans`（账号槽位贪心装箱）+ 商品 `limit` | C 端只做「单买家限购校验」；代购侧账号装箱逻辑不受影响 |
| 服务器与鉴权先例 | Supabase Edge Functions（qq-relay/typesafe-proxy）、relay 限频/白名单纪律、admin token 会话 | C 端服务端逻辑（下单/支付回调）走 Edge Function，鉴权/限频/超时纪律照抄 |

**结论：C 端约七成数据与链路已有，核心新建 = 买家端 UI + 购物车/下单服务端接口 + 支付通道。**

## 二、功能清单（对标淘宝 + 谷圈团购特性）

### A. 商品选购

- **首页**：进行中团期卡片流（封面图、活动名、IP、截团倒计时、商品数、进度标签）；顶部搜索框（活动名/商品名/日文原名/系列 IP 全文匹配）；制品类型快捷入口（吧唧/亚克力/色纸/卡套…，取 `typeMeta`）。
- **团期详情页**：团购规则说明（截团时间、发货预估、国际运费规则、退改政策）+ 商品网格（图、名称+原名、人民币价+外币原价、限购角标、已订进度条）。
- **商品详情页**：图集（参考图转存自有图床，v3.9.2 通道现成）、价格（售价+外币原价）、规格说明、**限购规则**（单买家限 n 件）、购买须知（预售周期与「谷子预售不退不换」等站方条款位）。
- **筛选排序**：价格/上架时间/销量（下单数聚合，`productStats` 同源）。

### B. 购物车与下单

- **购物车**：跨团期分组展示；数量步进（前端即时校验限购，服务端下单时复核）；失效商品自动标记（已截团/下架，不可结算）；勾选结算、全选。
- **下单确认页**：收货地址（从地址簿选/新建，复用 `d.addresses` 语义但按 P3 拆独立表）；金额明细 = 商品总额 + **预估国际运费**（按 `intl` 口径预估展示，实际以到货分摊为准，与团员端「我的国际费」口径一致）+ 国内邮费/包邮门槛（团期级配置）；订单备注。
- **下单（服务端）**：锁量校验（限购、截团、下架）→ 写订单（落 `orders`，状态「已下单/待付款」）→ 返回订单号。**价格一律服务端按主档计算**，前端金额仅展示。
- **超时关单**：待付款订单 N 小时（默认 24h）未支付自动释放（Edge Function scheduled，先例：relay 分钟级轮询）。

### C. 支付（三问之一，详见第三节）

- **V1 半自动（无主体即可用）**：下单后展示**收款码**（囤货地配置现成）+ **订单唯一金额尾数**（订单金额加 0.01–0.99 随机分，如 ¥58.27，唯一分位 = 订单指纹）→ 买家转账时**无需上传任何凭证**；管理端「账单核销」工具上传支付宝/微信导出的账单 CSV，按金额尾数+时间窗自动匹配核销（失败单进人工兜底队列）。QQ 侧可再加 bot 监听转账提醒辅助（可选，不依赖）。
- **V2 支付宝当面付（个体户/小微可申请，费率 ~0.6%）**：服务端预下单生成**动态收款码**（金额已含唯一尾数），买家扫码支付后**支付宝异步回调 notify_url（Edge Function）自动核销订单**——扫码体验不变，但买家零操作核销、管理员零对账。
- **V3 微信跳转（商户号 + 备案域名）**：微信 H5 支付（站外浏览器拉起微信）/ JSAPI（微信内置浏览器）真·自动跳转 + 回调核销；至此双通道全自动。

### D. 信息（物流与消息）

- **订单列表**：状态 tab（全部/待付款/已付款/已发货/已完成）；订单卡片（缩略图、团期、件数、金额、状态徽章、主操作按钮：去支付/查看物流/确认收货）。
- **订单详情**：状态时间线（已下单 → 已付款 → 采购中 → 国际到货 → 国内已发 → 已完成，复刻 `progressChain` 口径）+ 物流跟踪（快递单号复制 + 可选快递 100 轨迹查询）+ 商品清单 + 金额明细。
- **通知中心**：公告 + 到货/发货/催缴/支付成功通知（复用 `notify`）；QQ 私聊推送照旧（绑定过 QQ 的买家自动覆盖）。

### E. 个人资料

- 资料：CN（圈名）、QQ（绑定 bot，F10 唯一性校验沿用）、**手机号**（新增，选填；展示一律脱敏尾号）、收货**地址簿**（多条 + 默认地址，替代现有单条 `addresses[cn]`）。
- 账号动作：改圈名申请（`cnChanges` 沿用）、换囤货地申请（`transfers` 沿用）、退出登录。
- 客服：转人工 → QQ 工单台（v3.21.0 现成）。

### F. 管理端增量（小）

- 橱窗管理：商品「上架/下架/橱窗文案」开关（`activityMeta[].products` 加 `listed`/`blurb` 字段）；团期「开放选购/截团」开关 + 团购规则文案 + 国内邮费/包邮门槛。
- 订单池：C 端订单混入现有订单管理（buyer=CN 天然一致），新增「待付款」状态筛选与手动核销/关单入口。
- 账单核销工具（V1）：上传账单 CSV → 尾数匹配 → 批量核销/标记异常。

### 状态机

```
已下单(待付款) → 已付款 → 采购中 → 已到货(归批次) → 已发货 → 已完成
      └─(超时/取消)→ 已关闭                       └─ 售后(走工单)
已付款及之后 ≙ 现有 orders.paid/status/batchId/shipping 链路
```

## 三、支付方案调研（能否直接跳转微信/支付宝？）

**结论先行：无营业执照（个人身份）无法获得官方「自动跳转」能力；但「扫码 + 免上传凭证 + 自动核销」存在官方正解（支付宝当面付）。** 分层如下：

### 3.1 官方通道（2025–2026 现状）

| 通道 | 主体要求 | 体验 | 费率 | 关键约束 |
|---|---|---|---|---|
| 支付宝当面付 | **个人可有条件开通**（小微商户：身份证+经营场所照片等；个体户更稳） | 买家扫码（动态码，金额含唯一尾数）→ **notify_url 异步回调自动核销** | ~0.6%（无执照不可下调；个体户可谈 0.38% 起） | 需「经营场所照片」等材料；回调端点需公网 HTTPS（Supabase Edge 现成） |
| 支付宝手机网站/电脑网站支付 | 企业/个体户 + **ICP 备案域名** | 真·跳转支付宝收银台 | 0.6% | 网站支付产品审核要求备案域名 |
| 微信 H5 支付（站外拉起微信） | 商户号（企业/个体户；小微需门头照等经营凭证） + **支付域名 ICP 备案**（硬性） | 真·跳转微信 | 0.6% | 备案域名 + HTTPS |
| 微信 JSAPI（微信内支付） | 商户号 + 已认证公众号或小程序 APPID + **备案域名授权目录** | 微信内一键支付 | 0.6% | 公众号/小程序认证 ¥300/年 |
| 微信小程序支付 | **非个人主体**小程序 + 商户号 | 小程序内原生支付 | 0.6% | 个人主体小程序**不能**接入微信支付；小程序自 2023-09 起需备案 |

### 3.2 无官方主体的替代通道（评估后均不推荐作为正式方案）

- **第三方个人聚合（虎皮椒/PAYJS 类）**：个人可接、有跳转，但费率高（~2.5–3.8%）、资金过第三方手（跑路/冻结风险）、属灰色地带。**不推荐**。
- **个人收款码监听（V免签/码支付类自建）**：免费但掉单率高、依赖挂机 App，**违反微信/支付宝用户协议，收款码易被风控限制**。**不推荐**。
- **保持现状（展示收款码 + 买家上传凭证 + 人工审核）**：即现有 `payments.receipt` 流程，买家体验最差（你明确要避免的模式）。

### 3.3 推荐路线（回答「扫码付款能否免上传凭证」）

**能。** V1 用「**唯一金额尾数 + 账单自动核销**」：每单金额加随机 0.01–0.99 分位作订单指纹，买家只管转账（备注订单号更好但不强制），管理端把支付宝/微信**导出的账单 CSV 上传系统自动匹配核销**——买家不传截图、管理员不逐笔比对；兜底队列处理极少数匹配失败单。V2 换当面付后连账单上传也省掉（回调直核销），且当面付**个人即可申请**，是首个零执照的自动化节点。V3 补微信官方跳转（需个体户+备案）。

## 四、部署方案评估（现方案能否支撑运营？）

**结论：静态托管（GitHub Pages）+ Supabase 的架构本身可以支撑购物 C 端的浏览/购物车/下单/资料全流程**——重活全在 Supabase（表 + RPC + Edge Functions 回调），Pages 只是静态壳，与现状同构。**不能直接支撑的是三件事**，均有明确改进路径：

### 4.1 缺口与改进

1. **支付回调端点**：当面付 notify_url 只要求公网 HTTPS 可达——**Supabase Edge Function 现成满足，零备案**；但申请微信 H5/JSAPI 时**强制要求 ICP 备案域名** → 改进：注册域名（¥60/年）+ 用现有 SWAS（阿里云轻量）做备案主体，Edge 经备案域名 Caddy 反代（先例：qq-relay）。
2. **国内访问质量**：`github.io` 国内时通时断（现状已被接受，但 C 端是「零售」客群，首次打开流失不可逆）；`*.supabase.co` 国内直连延迟偏高。改进（V3 起按需）：备案域名 + 阿里云 OSS/CDN 托管前端静态资源（¥10–30/月量级）+ 备案域名反代 Supabase API。
3. **数据模型承载交易**：现有「单团一 JSONB blob」适合管理台账，**不适合订单交易**（并发锁量、幂等核销、行级权限都做不了）。改进：新增**独立表** `shop_products`（橱窗+锁量）/ `shop_orders`（C 端订单）/ `shop_payments`（支付流水）+ RLS + 服务端校验 RPC——B2 Phase 2「PII 拆表」设计储备正好在此落地。

### 4.2 小程序计划（远期 V4）

- 前端需以 **Taro/uni-app 重写**（vanilla JS 无法直接进小程序），但 **后端 API 全部复用**（Supabase RPC/Edge）——这是把 V1–V3 的服务端接口按「前端无关」设计的理由。
- 硬性前置：**非个人主体**（个体户即可）+ 小程序认证 ¥300/年 + 小程序备案；支付用微信 JSAPI（小程序内原生）。
- 价值判断：目标客群在 QQ 群，H5 先行已够；小程序是「客群外扩 + 信任感」选项，**不作为前三个版本的前置**。

### 4.3 成本汇总（估算，2026-09 市价）

| 项 | 费用 | 何时需要 |
|---|---|---|
| 域名（.com/.cn） | ¥55–80/年 | V3（微信通道）/反代（V2 可选） |
| ICP 备案 | ¥0（用现有 SWAS 出备案服务号，流程 1–3 周） | V3；V2 反代可选 |
| 个体工商户注册 | ¥0 自办（1–2 周）～ ¥800 代办 | V2（当面付更稳）/ V3 必须 |
| 支付宝当面付 | 无固定费，~0.6%/笔 | V2 |
| 微信支付商户号 | 无固定费，0.6%/笔 | V3 |
| 公众号/小程序认证 | ¥300/年 · 项 | V3（JSAPI）/ V4 |
| 前端国内托管 OSS+CDN | ¥10–30/月 | V3 起可选（体验优化） |
| Supabase | 免费档起步；Pro $25/月（超出 500MB/5GB 出口/50万 Edge 调用时） | 按量 |
| 短信验证码（若启用） | ~¥0.045/条 | P3 登录升级时 |
| **起步合计（V1→V2）** | **≈ ¥60/年 固定 + 0.6% 交易费 + 个体户 0–800 一次性** | |

## 五、安全评估（「密钥 + CN/QQ」够不够？）

**结论：用于现在的查询型团员端可接受（v3.4.0 已做 PII 裁剪 + 写白名单 + 空 p_cn 封堵）；用于带支付的购物 C 端不够，必须升级。** 缺口与升级路线：

### 5.1 现有模型的四个缺口（支付场景下被放大）

1. **团队级共享密钥**：`member_key` 所有买家设备上各存一份，泄露面 = 买家数；泄露后果 = 读全员订单与名单（PII 已裁剪但订单/名单仍在）。
2. **身份是「自报家门」**：CN/QQ 是输入字符串而非凭据——知道他人 CN 即可看他人订单、以他人名义下单/改地址。查询可容忍，**交易与支付不可容忍**。
3. **无服务端算价/锁量**：价格、限购、截团全在前端 blob，恶意客户端可绕过；支付金额必须服务端计算并防篡改。
4. **匿名 RPC 无限频、无审计**：可脚本枚举刷接口；出交易纠纷无法举证。

### 5.2 升级路线（随版本落地）

- **P1（V1 上线门槛）**：C 端「密钥+CN」降级为一次性校验凭据 → 服务端签发**个人 session token**（短期、绑定 CN、可吊销；先例 = admin_sessions 表同款纪律）；匿名 RPC 全部加限频（relay 纪律照抄）；下单/改地址只走**新服务端 RPC**（校验限购/价格/截团），不开放团员整包写入口给 C 端。
- **P2（支付上线门槛）**：C 端订单/支付流水进**独立表 + RLS**（按 CN/买家行级隔离，B2 Phase 2 落地）；金额服务端计算；**支付回调幂等核验**（金额+签名+订单状态机）+ 审计日志（先例 `admin_audit_log`）。
- **P3（正规化）**：登录升级为**手机验证码 / QQ OAuth**（经 relay，先例 typesafe-proxy 隔离通道），密钥退场为管理员发放的一次性邀请码；手机号/地址 PII 独立表按行隔离；小程序走 `wx.login` + 手机号快捷获取。
- **PII 纪律（全程）**：手机号选填、展示一律脱敏尾号（先例：审计尾号）、只走 HTTPS、不再进共享 blob。

| 版本 | 主题 | 内容 | 前置 |
|---|---|---|---|

## 九、拍板与实施记录（2026-09-30，V1 = v3.22.0 已实施）

> 用户拍板：①支付**直接使用 V1**（唯一尾数+账单核销）；②客群**暂时仅本团成员**；③登录**取消密钥发放**，
> 按「QQ/微信 OAuth > 手机号验证 > 邮箱验证」的偏好调研落地；④订单数据**直接与原管理端数据库合并同步**（不拆独立表）。

### 9.1 登录方案调研（回答「手机验证码需要什么部署？邮箱验证码是否可行？」）

| 方案 | 部署要求 | 费用 | 结论 |
|---|---|---|---|
| **邮箱验证码** | Supabase Auth 原生（signInWithOtp + verifyOtp）：**零额外部署**；一次性配置 Dashboard→Authentication→Email Templates 让模板含 `{{ .Token }}`（6 位码，默认模板通常已含） | ¥0（免费档自带频控） | **V1 已实施**——QQ 邮箱可达（提醒垃圾箱） |
| 手机验证码 | 两条路线：①Supabase Auth Phone（Twilio/MessageBird/Vonage 为 provider）——需海外信用卡充值，中国号码可达但 ~¥0.3–0.5/条、到达率一般；②国内短信（阿里云短信）——需签名+模板审核，验证码类签名个人可申请但需佐证材料（备案网站/小程序/公众号之一），¥0.045/条 | ①贵且不稳；②便宜但门槛在资质 | **暂缓**——有主体/备案后接入，作为第二优先 |
| QQ OAuth | QQ 互联（connect.qq.com）个人开发者可申请网站应用；**硬前置 = ICP 备案域名** + 审核数日；返回 openid ≠ QQ 号（仅作登录身份，与 `memberMeta.qq` bot 绑定机制不冲突） | ¥0（域名已列 V3 成本） | **备案后升级为首选（V2）** |
| 微信 OAuth | 网站应用需微信开放平台+企业资质；公众号网页授权需**已认证服务号**（个人主体不可认证） | 认证 ¥300/年 | **暂缓**——有主体后评估；小程序 wx.login 归 V4 |

落地顺序 = 邮箱验证码（V1，唯一即刻可用）→ QQ OAuth（V2，备案域名后）→ 手机验证码（有资质后）→ 微信（有主体后）。

### 9.2 数据合并模型（用户拍板：直接并入管理端同一份 blob）

- `d.shopOrders[]`：C 端订单头（no/total/tail/paidTotal/status/addr 快照/remark/items）；
- `d.orders[]`：**逐商品落单行**（buyer=CN + shopOrderId/shopOrderNo 关联）——管理端到货分批/国际费分摊/审批/发货/快递单号/团员端查询**全链路零改造**；
- `d.shopUsers{[auth.uid]: {cn,email,boundAt}}`：登录绑定映射（一 CN 一账号，换绑找团长）；
- 写入纪律：security definer + 服务端算价/限购/截团校验 + 写前历史快照（B1）+ `for update` 行锁（与管理端乐观锁写入串行化）；
- 风险声明：blob 单行模型在**本团规模**（数十买家、低频下单）+ 行锁下够用；上量后仍建议拆独立表（B2 Phase 2 储备），本次拍板不做。

### 9.3 V1 已实施范围（v3.22.0）

- **服务端**：`supabase-schema.sql` F12 节 7 个 RPC（shop_ctx 内部 + shop_me / shop_bind_cn / shop_get_catalog / shop_place_order / shop_get_my_orders / shop_cancel_order）+ `supabase/migrations/001-shop-v1.sql`（幂等迁移）；
- **C 端**：`shop.html` + `css/shop.css` + `js/shop.js`——邮箱 OTP 三步登录 → 绑定 CN → 橱窗（团期流/搜索/商品详情）→ 购物车（本地 + 限购夹紧）→ 下单（服务端算价）→ 收银台（尾数 + 囤货地收款码 + 转账指引，**买家零凭证上传**）→ 订单（状态 tab/时间线/快递单号/取消待付款）→ 我的；
- **管理端**：活动管理展开区商品卡新增「上架到 C 端商城橱窗」开关（`products[].listed`，缺省下架；需登记单价才可上架）；团期开放 = `shopOpen===true` 或活动状态「进行中」；C 端下单自动生成 `type:'shop'` 通知到通知中心；
- **鉴权**：C 端零密钥——Supabase Auth 邮箱 OTP + auth.uid()；六个对外 RPC 仅 authenticated 可执行，shop_ctx（含整 blob）revoke 全员仅 definer 内部；
- **测试**：tests/shop-v1.test.js 17 例（纯函数/RPC 错误分支/橱窗开关持久化），全套 519→536 全绿。
