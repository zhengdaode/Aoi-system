# 调研报告：多人同时使用时「第二人保存失败 / 刷新丢内容」的原因与方案

> 对应需求 3（2026-11-10 用户反馈）：目前网页不支持多人同时使用——第一人做出更改后，
> 第二人的修改无法保存，需刷新页面，而刷新又会导致已填写的内容丢失。
> 本报告只调研与给方案，不改代码；批准后按 §5 版本切分实施。

## 一、结论先行

1. **这不是数据库/服务器的限制**。Supabase（PostgreSQL）本身完全支持多人并发读写；
   现象是本项目**有意设计的写入策略**造成的：全部业务数据存在 `team_data.data` 一个
   JSONB blob 里，每次保存 = 整包覆盖写，且携带乐观锁（`expected_updated_at`）——
   B 保存时若 A 已先写过（版本号变了），服务端直接拒绝并提示「数据已被他人修改，请刷新后重试」。
2. 乐观锁本身是**正确的安全底线**（防旧页面整包覆盖别人的新数据，v3 之前真实发生过覆盖事故），
   问题在于锁的粒度太粗：**锁的是整份 blob，而不是「用户正在改的那一小块」**。
   A 只改了自己负责的购买状态，B 的整包保存就被拒——即使两人改的字段毫不相干。
3. 刷新丢内容是前端形态问题：表单值存在 DOM 里，刷新即失；与数据库无关。

## 二、现象的精确定位（代码链路）

| 环节 | 位置 | 行为 |
|------|------|------|
| 唯一写入口 | `js/data.js` `Aoi.saveTeamData` | 整包 `data` + `Aoi.adminUpdatedAt`（上次版本）发 RPC |
| 服务端锁 | `supabase-schema.sql` `admin_save_team_data` | `expected_updated_at` 与 `team_data.updated_at` 不一致 → `raise exception '数据已被他人修改，请刷新后重试'`（schema.sql 约 1027-1030 行） |
| 前端处置 | `js/data.js` + `Aoi.explainRpcError` | toast「请刷新页面重新进入后重试」，并 `Aoi.adminUpdatedAt = null`（本次保存丢弃） |
| 团员端同理 | `update_team_data_by_member_key` | 同款乐观锁，同样整包覆盖 |
| 刷新丢内容 | 各视图表单 | 未保存的输入只存在于 DOM / 模块临时变量，`location.reload()` 即失 |

时间线还原：A、B 同时打开页面 → 各自读到版本 T0 → A 先保存，服务端版本变 T1 →
B 保存时携带 T0 ≠ T1 → 被拒。**A 与 B 即使改的是不同活动、不同字段，也会撞锁**——
因为锁在整包粒度上。blob 越大（现已 2MB 预警）、改动越频繁，撞锁概率越高。

## 三、是否是数据库/服务器的限制？（详细拆解）

- **Postgres 行级写并发**：`UPDATE ... SET data = ...` 带 `WHERE` 的并发写完全没问题，
  行锁自动排队；不存在「第二人写不进」的数据库层限制。
- **Supabase 免费档限制**：连接数、带宽、Realtime 并发有配额，但都远高于本团规模
  （团长管理端为个位数管理员 + 团员自助只读为主），不构成瓶颈。
- **RPC 限频**：自建 RPC 无限频（shop 系 RPC 有限频是另一回事）。
- **网络/服务器在线**：blob 单行 ~2MB 量级，读写延迟可接受。
- 所以：**限制 100% 来自应用层的「单 blob + 整包乐观锁」设计**，是可以分阶段改造掉的。

## 四、可选方案（按侵入性从小到大）

### 方案 A · 治标：保存失败不丢内容 + 自动合并重试（不动数据模型，改动最小）

1. **草稿不丢**：保存被拒时，把本次改动连同服务端最新 blob 一起留在内存，
   toast 改为「数据已被同事更新——已自动合入最新数据，你的修改已保留，点重试即可保存」。
2. **字段级自动合并**：前端记录本次会话动过的字段集合（dirty keys），重试时
   以「服务端最新 blob 为底、只覆盖自己动过的字段」重新打包上传，乐观锁换新版本再试。
   两人改不同字段 → 自动合并成功；改同一字段 → 保守丢弃后改、提示谁改的。
3. 顺带修「刷新丢内容」：关键长表单（录入/展开区）把未保存草稿写 `sessionStorage`，
   刷新后回填。
- 优点：零 schema 改动、零迁移、一两个版本可落地；缺点：仍是整包上传（大 blob 慢），
  同字段并发仍需人工裁决；「看到别人改动」仍需手动刷新。

### 方案 B · 治本（轻）：分片写入 + Realtime 实时同步（推荐主路线）

把「整包读写」改成「按业务键分片读写」+ 订阅变更：

1. **写路径分片**（新增 RPC，旧 RPC 保留为兜底）：
   - `update_orders_slice(p_keys jsonb)`：按订单 `id` 列表 upsert；
   - `update_activity_meta_slice(p_name, p_patch jsonb)`：按活动名 `jsonb_set` 合并；
   - `update_limits_slice / update_paigu_slice / update_reservoirs_slice ...` 同理。
   每个 RPC 内部 `for update` 行锁 + `jsonb` 深合并，**只锁自己改的那一片**，
   A 改购买状态与 B 改活动备注互不相撞；服务端仍保留整包快照存档（历史快照机制照旧）。
2. **读路径增量**：登录仍整包首拉；此后经 **Supabase Realtime**（`postgres_changes`
   订阅 `team_data` 行）收到变更通知 → 拉取增量或整包做**字段级合并进内存**
   （后写者覆盖同字段，其余字段保留本地未保存状态），页面不刷新即看到别人改动。
   Free 档 Realtime 对本团规模够用；不可用时降级为「30s 轮询 updated_at，变了就提示可刷新」。
3. **冲突裁决**：分片写基本消除撞锁；残余同字段并发由「后写覆盖 + 被覆盖方 toast 提示」兜底
   （业务上是极小概率，且每片改动都留痕于现有日志/通知体系）。
- 优点：多人同改同一活动成为常态；blob 上传量大幅下降（只传改动片）；实时可见。
- 缺点：RPC 数量增多、需一次迁移；前端所有「改内存 → saveTeamData 整包」调用点
  需改为「改内存 → 对应 slice RPC」（约 20+ 调用点，机械改）。

### 方案 C · 治本（重）：业务数据出 blob、拆规范表

订单/活动/计划/排位拆成独立表（orders/activities/...），行级并发天然成立，
配合 Realtime 即时看到别人改动。最彻底，但等于一次小型重写 +
全量数据迁移 + 团员端 RPC 重写，且失去「单 blob 快照/恢复」的运维便利。
**不建议现在做**；方案 B 的 RPC 划分天然为将来拆表铺路。

### 方案 D · 协作增强（选配，叠加在 B 上）

- 多人在线状态（谁在看哪个活动，Realtime presence）；
- 同字段冲突的「行级占位提示」（有人在编辑时输入框标黄）；
- 操作留痕通知化（谁改了哪笔订单的购买状态，推送进通知页）。

## 五、建议的实施切分（若批准）

| 版本 | 内容 | schema |
|------|------|--------|
| v3.34.x（方案 A） | 保存失败草稿保留 + dirty-keys 字段级自动合并重试 + 长表单 sessionStorage 草稿 | 零 |
| v3.35.x（方案 B-1） | slice RPC（订单/活动 meta/限购/排位四个最热切片先行）+ 前端写路径切换 + Realtime 订阅与降级轮询 | 新增 RPC（幂等迁移） |
| v3.36.x（方案 B-2） | 其余切片（蓄水池/类型/囤货地/批次...）+ 同字段冲突提示 + 多人在线 presence（选配 D） | 零 |

上线顺序上 A 与 B 可独立发布：A 先保住「不丢内容」，B 再解锁「真并发」。
每步都保留旧整包 RPC 兜底（slice 失败自动回落整包），数据事故面可控。

## 六、需要拍板的点

1. 方案路线：A 先行（最小改动）还是 A+B 一起批（A 作为 B 的前置一步到位）？
2. Realtime 是否启用（Free 档并发配额够用；不启用则退化为轮询提示）。
3. 同字段冲突的裁决口径：后写覆盖 + 提示（推荐）还是弹窗人工选择？
